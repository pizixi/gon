# 性能检查与优化

本次保持终端协议、搜索顺序、大小写规则、宽字符与组合字符列位置、回滚行数和字形像素不变，优化历史搜索和人工加粗字形的临时缓冲区。

## 已完成

### 历史搜索

`internal/ui/pane.go` 原先先为整行生成 rune 和列号数组，再逐位置比较查询。未找到结果时，回绕搜索还可能再次扫描已经访问的历史行。重复前缀的查询会反复比较相同字符，最坏时间复杂度为 O(文本长度 × 查询长度)。搜索期间持有窗格锁，耗时也会影响输出解析。

现在直接遍历单元格，使用 KMP 匹配，并只保留查询长度的列号窗口；将回绕前后的行范围分开，每行最多扫描一次。保留每个显示行的第一个匹配、正向/反向回绕、空白单元格，以及组合字符和宽字符的原有选择位置。

### 人工加粗字形

`internal/render/atlas.go` 的人工加粗需要把同一轮廓绘制五次。原先每次创建光栅器，都会分配覆盖率工作缓冲区；现在在五次绘制之间调用 `Reset`，清空并复用同一缓冲区。复用范围限定在一次字形光栅化内，不增加长期缓存。

## 测量结果

Windows/amd64，Go 1.27.4，Intel Xeon E3-1240 V2。每项运行三次，以下取中位数。搜索使用 120 列、24 行可见区和 8000 行已填满的历史；表中三项搜索均为未命中场景。

| 场景 | 修改前耗时 | 修改后耗时 | 修改前临时分配 | 修改后临时分配 |
| --- | ---: | ---: | ---: | ---: |
| 普通英文日志搜索 | 45.75ms | 9.25ms | 3056B / 15 次 | 128B / 2 次 |
| 中文、重音和 emoji 日志搜索 | 48.87ms | 11.27ms | 3056B / 15 次 | 0B / 0 次 |
| 重复前缀查询 | 220.61ms | 10.61ms | 3264B / 16 次 | 1040B / 3 次 |
| 32px 字形首次人工加粗光栅化 | 21.80μs | 20.25μs | 17270B / 11 次 | 4977B / 7 次 |

搜索耗时下降约 77%–95%，人工加粗的临时分配字节下降约 71%。普通字形光栅化的分配量保持 3633B / 7 次。

这些是指定工作负载的函数级基准，不能直接等同于整机 CPU、进程常驻内存或所有交互的改善比例。字形图集命中时不会重新光栅化，因此人工加粗的收益主要发生在首次遇到该字形、字号或缓存淘汰后。短查询的堆分配结果也受 Go 版本影响。

复现命令：

```powershell
go test ./internal/ui ./internal/render -run '^$' -bench 'Benchmark(FindHistory|Rasterize)$' -benchmem -benchtime=300ms -count=3
```

## 后续优先关注

1. **回滚历史是主要的长期内存来源。** amd64 下一个 `Cell` 为 40B；以 120 列、8000 行计算，仅历史单元格约占 36.6MiB/窗格，另有行索引、组合字符串等。历史随输出逐步增长。短行仍通常保存整行单元格，可以研究压缩行尾默认空白，但需要同时处理空白位置的选取、搜索、复制、换行与窗口缩放，避免改变行为。本次没有缩减配置的历史行数。
2. **大量连续输出仍会复制整个可见滚动区域。** `Screen.scrollUp` 每次滚动会移动单元格数组，输出量很大时值得用实际 shell/TUI 工作负载做 CPU profile。改为可见行环形存储涉及光标、滚动区域和备用屏幕，适合单独验证后再改。
3. **绘制期间持有窗格锁。** `drawTerminal` 在锁内遍历单元格并查找或光栅化字形。首次显示大量不同 CJK 字形或 emoji 时，可能延迟解析线程。是否引入可见区快照，应先测锁等待；快照本身会增加复制和内存开销。

项目已有的输出约 30fps 合并、后台标签页和最小化抑制刷新、光标空闲停止闪烁、按需加载字体、有上限的字形缓存，以及壁纸降采样均已存在。这些机制值得保留，继续降低刷新率或回滚上限会改变体验，不属于本次优化。

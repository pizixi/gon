# TUI 拖选高亮跟随

Gon 自己的文本选区可以在当前帧直接更新。Codex CLI 等应用开启鼠标上报后，选区由应用绘制，位置必须先经过鼠标事件、输入队列、ConPTY，再由应用输出颜色或反色指令返回 Gon。

此前的 c6c5b59 只更新本地选区的鼠标预览，应用鼠标路径仍逐条转发排队的旧位置；返回的高亮画面还会经过普通输出的约 33ms 合并等待。这两处都会增加高亮落后鼠标的时间。

本次调整：

- 合并一帧内连续的鼠标拖动，只处理最后的位置。在帧末使用 Windows 当前鼠标位置更新本地选区或应用的左键拖动上报。仍使用已经绘制的窗格网格，支持分屏、DPI 缩放和像素坐标上报。
- 按下、松开、取消、修饰键变化和其他输入是合并边界，先处理此前的拖动，再处理边界事件。松开使用事件本身的坐标，取消使用最后上报的位置。当前鼠标读取失败时使用最后排队的事件。
- 上报鼠标后的 150ms 内，可见窗格的输出立即请求刷新，包含松开后的最终高亮。普通输出继续约 30fps 合并，后台窗格和最小化窗口沿用原有刷新策略。
- 保留应用的同步输出协议；应用尚未完成一帧时，继续显示之前的完整画面。

## 验证

一帧积压 64 个拖动事件的回归场景只向应用发送 1 个拖动位置，避免占满输入队列。测试覆盖拖动/全鼠标跟踪、像素编码、分屏、高 DPI、当前鼠标读取失败、Ctrl/Alt 变化、键盘输入边界、松开、取消和 Shift 本地选区。

真实 ConPTY 测试启动独立的控制台程序，开启 SGR 鼠标跟踪，以同步输出绘制自己的蓝色选区。尚未发送松开事件时，屏幕缓冲已经显示从锚点到最新鼠标位置的完整高亮，随后仍能接收松开。

    go test ./internal/ui -run 'Test(TUI|ShiftSelectionInTUI|MouseResponse|TerminalDrag)' -count=1 -v
    go test ./...
    go vet ./...

针对本次改动的竞态检查也已通过。此环境使用 MinGW GCC 8.1，静态链接可避免动态运行库的入口缺失：

    $env:CGO_ENABLED = '1'
    $env:CGO_LDFLAGS = '-static'
    go test -race ./internal/ui -run 'Test(TUI|ShiftSelectionInTUI|MouseResponse|TerminalDrag)' -count=1

这些检查验证事件转发、输出调度和 ConPTY 往返。实际 Codex CLI 与 RDP 会话的体感仍需复测；应用自身处理时间、图形呈现和网络延迟仍会影响最终跟随速度。
